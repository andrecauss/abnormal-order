17 · Governança

Regra · doc §17

O domínio de governança controla permissões e rastreabilidade.

Em poucas palavras

Diz quem pode agir.

Guarda o rastro do que mudou.

17.1 · Permissões

Regra · doc §17.1

Uma tabela de permissões define quais usuários podem executar ações como:

  • ajustes;
  • uploads;
  • liberações;
  • ações manuais.
Em poucas palavras

Uma tabela diz quem pode fazer o quê.

Sem permissão, não ajusta, não sobe arquivo, não libera.

17.2 · Auditoria

Regra · doc §17.2

O sistema mantém rastreabilidade das alterações relevantes.

Exemplo:

  • override manual de quota;
  • usuário responsável;
  • data/hora;
  • valor original;
  • valor alterado.
Em poucas palavras

Toda mudança importante fica registrada.

Quem, quando, antes e depois.

É o único freio sobre o Manual Release.

Ilustrativo · registro de auditoria
Usuário = ana.silva
Data/hora = 12/06 14:32
Ação = override de quota
Valor original = 0
Valor alterado = 40

17.3 · Uploads

Regra · doc §17.3

O mesmo modelo de arquivo pode ser utilizado para refletir liberações no sistema.

O arquivo não precisa identificar o motivo da liberação.

A lógica que decidiu a liberação ocorre antes do upload.

Em poucas palavras

Um formato de arquivo para as liberações por upload.

O arquivo não diz o porquê.

A decisão vem antes; o upload só registra.

Esclarecido na revisão de 27/09

Seção 20.1 do doc

Pergunta: Dois pedidos do mesmo Customer–PN em paralelo geram race condition no acumulado?

Decisão: Não acontece — limitação sistêmica impede processamento paralelo real. Fechado como fato; não é necessário lock.

Seção 20.4 do doc

Pergunta: O que acontece com overrides ou liberações manuais concorrentes no mesmo Customer–PN?

Decisão: Não há regra sistêmica de precedência — autoridade do usuário é absoluta. Governança inteiramente via trilha de auditoria.
